# DMC POSE Architecture V2 — 요구사항 기준선

상태: 설계 초안  
범위: `/home/dmc/AI/DMC_POSE` 실시간 병상 모니터링 및 낙상 추론  
원칙: 이 문서가 합의되기 전에는 기존 런타임 코드를 구조적으로 변경하지 않는다.

## 1. 시스템 목표

여섯 병상의 영상을 지연 없이 모니터링하면서, 중앙 서버 한 대의 제한된 자원을 공유하여 침대 주변 사람의 낙상 가능성을 실시간으로 계산한다.

시스템은 다음 두 결과를 독립적으로 제공해야 한다.

1. 사람이 눈으로 확인할 수 있는 빠른 실시간 영상
2. 프로그램이 소비할 수 있는 카메라별 AI 상태값과 낙상 후보

## 2. 확정된 운영 조건

- 카메라는 RPi에 연결되어 있다.
- RPi는 H.264 RTSP 스트림을 약 20 FPS로 송출한다.
- 대상 카메라는 여섯 대다.
- AI 가중치는 중앙 자체 서버에서 로드하고 실행한다.
- RPi에서는 무거운 AI 추론을 실행하지 않는다.
- 중앙 서버의 GPU와 CPU는 여섯 카메라가 공유한다.
- 침대 segmentation, 사람 pose, 6-class 자세 분류, TCN 시계열을 하이브리드로 사용한다.
- 사람이 없는 카메라에는 무거운 추론을 상시 실행하지 않는다.
- 급격한 움직임은 싼 감시기가 빠르게 발견하고 비싼 추론을 깨운다.

## 3. 절대 요구사항

### R1. 영상과 AI 분리

AI 처리 속도가 느려지거나 모델이 재시작돼도 모니터 영상은 계속 표시돼야 한다.

### R2. 최신성 우선

AI는 오래된 프레임을 순서대로 처리하지 않는다. 처리 능력이 부족하면 중간 프레임을 버리고 항상 가장 최신 프레임을 사용한다.

### R3. 침대 자동 기준점

침대 segmentation으로 병상 mask/bbox를 자동 생성한다. 안정화된 ROI는 캐시하고 매 프레임 다시 계산하지 않는다.

### R4. 빈 카메라 절전

사람이 없을 때 Pose, 6-class, TCN을 계속 실행하지 않는다. 단, 새로운 사람을 발견하기 위한 저비용 모션 감시와 희소 person probe는 유지한다.

### R5. 빠른 사건 깨우기

침대 주변에서 급격한 영상 변화가 감지되면 해당 카메라만 즉시 고속 분석 상태로 전환한다.

### R6. 시간축 보존

모든 AI 관측에는 capture timestamp와 inference timestamp를 별도로 기록한다. TCN에는 학습 주기와 동일한 실제 시간 간격의 입력만 전달한다.

### R7. 단일 신호 판정 금지

다음 신호 중 하나만으로 낙상을 확정하지 않는다.

- frame difference 또는 optical flow
- 한 프레임 자세
- 침대 밖 판정
- TCN 단일 확률

### R8. 카메라별 격리

한 카메라의 RTSP 오류나 추론 지연이 다른 다섯 카메라의 영상과 상태 갱신을 막지 않아야 한다.

### R9. 관측 가능성

각 카메라에 대해 최소한 다음 값을 확인할 수 있어야 한다.

- 스트림 연결 상태
- 마지막 capture 시각과 프레임 나이
- 현재 분석 상태
- 침대 ROI 준비 여부와 갱신 시각
- 사람 존재 여부와 마지막 확인 시각
- 모션 점수
- Pose 실행률
- TCN buffer 상태와 확률
- 전체 지연과 최근 오류

## 4. 역할 분리

### RPi

- 카메라 캡처
- H.264 하드웨어 인코딩
- RTSP/미디어 송출
- 연결 상태 제공

RPi는 침대 segmentation, Pose, 6-class, TCN을 실행하지 않는다.

### 중앙 AI 서버

- RTSP 추론용 구독
- 최신 프레임 버퍼
- 침대 ROI 관리
- 사람 존재와 모션 감시
- 상태 기반 추론 스케줄링
- Pose, 6-class, TCN
- 낙상 후보 융합
- 상태 API와 이벤트 기록

### 브라우저

- 실시간 영상 표시
- 중앙 서버의 AI 상태값 구독
- 영상 위에 상태, 확률, 경고를 UI로 합성

## 5. 목표 성능 초안

다음 수치는 설계 검증을 위한 초기 목표이며 실제 장비 측정 후 확정한다.

| 항목 | 초기 목표 |
|---|---:|
| 모니터 영상 표시 FPS | 카메라당 15 FPS 이상 |
| 모니터 end-to-end 지연 | 정상 LAN에서 1초 이하 |
| 빈 카메라 Pose probe | 0.5~1 Hz |
| 급격한 모션 감지 | 10~20 Hz |
| 사람 존재 시 v1 Pose | 실제 관측 10 Hz |
| burst Pose | 가능한 경우 10~20 Hz |
| 기존 TCN 입력 | 실제 시간 10 Hz, 30 sample |
| 상태값 전송 | 2~10 Hz |
| 프레임 backlog | 0, 최신 프레임 덮어쓰기 |
| 카메라 장애 격리 | 나머지 카메라 무중단 |

## 6. 설계 시 결정할 항목

### D1. 브라우저 영상 전송

권장안은 RPi/MediaMTX 또는 별도 미디어 게이트웨이의 WebRTC/LL-HLS를 브라우저가 직접 보고, 중앙 서버는 AI JSON만 제공하는 방식이다. 이 방식은 중앙 서버의 JPEG 재인코딩 부하를 줄인다.

검증이 안 될 경우 중앙 서버의 최신 프레임 기반 MJPEG를 fallback으로 사용한다.

### D2. person probe 구현

침대 segmentation 모델은 사람을 찾지 않는다. 빈 카메라에서 사람 유무를 확인할 모듈은 다음 중 실제 측정 후 선택한다.

- 저해상도 경량 person detector
- 저해상도 YOLO Pose 희소 실행
- 모션 발생 시 Pose 실행 + 정기 Pose probe

### D3. calm 모드의 TCN

현재 TCN은 실제 10 Hz Pose 입력을 전제로 한다. v1에서는 사람이 있으면 10 Hz Pose를 유지한다. Pose를 2~5 Hz로 줄이는 최종 절전 모드는 missing/stale mask를 포함한 TCN v2 재학습 후 적용한다.

## 7. 설계 제외 범위

현재 설계 단계에서는 다음을 하지 않는다.

- TCN shadow를 바로 실경보에 연결
- 현재 체크포인트에 임의로 20 Hz 입력
- 누락된 Pose를 숨기기 위한 무조건적인 프레임 복제
- 여섯 카메라의 모든 모델 상시 실행
- 로그의 HTTP 200만 보고 실시간성을 정상으로 판정

## 8. 합의가 필요한 핵심 문장

> 영상은 항상 빠르게 흐르고, AI는 최신 프레임을 상태에 따라 선택적으로 처리한다. 침대 ROI는 자동 생성 후 캐시하고, 빈 카메라는 싼 감시만 유지하며, 급격한 움직임이 발생한 카메라만 고속 Pose와 시계열 검증으로 승격한다.
